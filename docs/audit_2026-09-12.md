# mini-trantor 深度审计与研发收敛记录

审计基线：`3eba368`（本次开始时 main 与 origin/main 一致，工作区干净）。
实施分支：`audit/reactor-scope-reset`。日期：2026-09-12。

## 1. 结论

项目的主要问题是**扩张速度超过了生命周期合同的闭合速度**。
最初的“小型 Reactor”已演化为默认编译、安装的游戏框架、协议集合和传输实验集合，
而 coroutine frame、DNS 回调和线程关闭这些更底层的问题仍未解决。

决定把主线重新收敛为 TCP Reactor，撤销游戏框架、客户端协议生态和自研可靠 UDP 生产化方向。
已经实际裁剪源码、公开 API、CMake、测试和安装边界；没有仅通过 preview 标签掩盖依赖。
新的研发顺序是 S0 裁剪与工程证据 → S1 正确性阻塞项 → S2 最小 TCP 合同 → S3 负载与发布证据。

**本次完成范围审计、裁剪及若干直接修复；不宣称全库安全或已达到稳定发布条件。**
尤其下列三个问题已经实际复现，常规及 ASan 套件通过也不能关闭它们；完整 TSan 另有 8 项失败。
可独立运行的完整程序和编译命令见[缺陷复现](audit_repros.md)。

## 3. 未解决的阻塞项

### P0-01：挂起的 Task 析构后，timer 仍恢复已释放 frame（已复现）

证据：`mini/coroutine/Task.h:167` 的析构直接 destroy；
`mini/coroutine/SleepAwaitable.h:52` 的定时回调保留 handle 并 resume，awaitable 没有注销析构路径。
最小复现是在 owner loop 创建 task、start 等待 1ms、销毁 task，再运行 loop。
ASan 报告 `heap-use-after-free`，堆栈为 `coroutine_handle<void>::resume → SleepAwaitable → TimerQueue::handleExpired`。

```cpp
mini::coroutine::Task<void> sleeper(mini::net::EventLoop* loop) {
    co_await mini::coroutine::asyncSleep(loop, std::chrono::milliseconds(1));
}
// 在 main 中：
mini::net::EventLoop loop;
{ auto task = sleeper(&loop); task.start(); }  // frame 已释放
loop.runAfter(std::chrono::milliseconds(20), [&] { loop.quit(); });
loop.loop();  // 现状：定时回调恢复悬空 handle
```

同类静态风险存在于 ConnectionAwaiterRegistry 保存的裸 handle，以及已经 queueResume
但尚未执行的恢复闭包；这些扩展路径本次未逐个复现，不合并成“全部确认”。
修复应建立注销/销毁/恢复协议，覆盖 sleep/read/write/close、queued resume 与取消，
不能只在 SleepState 上加一个共享指针。列为 S1 首项，协程整体保持预览。

### P0-02：DNS 缓存命中回调可自锁；callbackLoop 生命周期也未闭合（前者已复现）

证据：`mini/net/DnsResolver.cc:74` 获取 cacheMutex，`92` 在锁持有期间 runInLoop；
若调用线程就是 callbackLoop owner，则同步执行用户回调。用户回调 clearCache（`114`）
再次申请同一个非递归 mutex，产生死锁。

复现顺序：enableCache → resolve("localhost") 等待成功 → 在其 owner-loop 回调再次 resolve
同 hostname → cache-hit 回调调用 clearCache。程序输出进入 clearCache 后停住，外部 4s
timeout 终止；没有输出 clearCache 返回。解决方案须先复制结果并释放 cache lock，再派发用户代码。

另一个静态风险是 worker 完成后直接通过 `callbackLoop` 裸指针 runInLoop（`200`）；
取消或销毁 TcpClient 不证明 loop 仍活着。需要请求范围或明确的 shutdown barrier。
只改 cache lock 不足以关闭 DNS 生命周期任务。

完整 TSan 还报告取消注册的实际竞争：`DnsResolver.cc:62` 的 registration.emplace
可与 callbackLoop 上 deliver 的 registration.reset（`25`）同时发生。该证据属于请求状态
发布问题，与缓存死锁是不同故障；需一并纳入 DNS 合同。

### P0-03：TLS 客户端默认不验证对端，hostname 仅设置 SNI（已核验）

`mini/net/TlsContext.cc:104` 加载默认 CA，但 newClientContext 未设置 SSL_VERIFY_PEER。
实际执行 `SSL_CTX_get_verify_mode(newClientContext()->nativeHandle())` 返回 0，
与本机 OpenSSL 的 `SSL_VERIFY_NONE` 相同。`ConnectionTransport.cc:63` 只调用
SSL_set_tlsext_host_name，当前代码没有 hostname verification 设置。

因此“握手/echo 成功”不能证明对端可信。现状保留 TLS 但默认关闭；S1 必须加入
默认验证、显式 insecure 模式和 hostname mismatch/untrusted certificate 拒绝合同。
本次未修改 TLS 身份语义，避免把一个默认值调整误当作完整安全修复。

### P1-04：await_suspend 发布后继续访问 awaiter（静态高风险）

`TcpConnection.h:193/212/231` 先 arm waiter，之后才读取 token/promise 并写 registration。
异线程调用时 owner loop 可能在 arming 后立即排队恢复，原 await_suspend 仍访问 this/frame。
SleepAwaitable 也先注册 timer，再建立 cancellation registration。
取消回调、timerId 和 registration 的跨线程发布顺序缺乏统一协议。

应把 arming/取消注册合并为 owner-loop 的受控状态转换，用同步屏障构造测试；
本次未声称 TSan 已证明全部这些竞争存在或已消失。

### P1-05：线程启动缺少失败状态；pool 停止与 loop 析构竞争（后者有 TSan 证据）

`EventLoopThread.cc:32` 的谓词只有 loop_ != nullptr。init callback 若调用 quit，
worker 发布指针后可以立刻退出并清空（`67`），启动方可能错过可观测的就绪状态而永久等待。
init callback 抛出也没有向调用者回传的失败状态。
`EventLoopThreadPool.cc:34` 停止时遍历缓存的 loop 指针；worker 若已自行退出，这些指针过期。

完整 TSan 的 thread_pool_stop 用例报告 worker 析构关闭 wakeup fd，与主线程经
pool.stop → quit → wakeup 写同一 fd 竞争。它验证了停止期间的资源寿命问题，
不等于已证明上述 init-quit 的每一种交错。

需要 Starting/Running/Stopped/Failed 状态与明确发布/停止合同。测试应覆盖 init-quit、
init-throw、自然早退、重复 stop；启动失败路径本次仍为静态定位。

### P1-06：其他必须继续审计的边界

- Channel enable/disable 先修改 events 再经 loop 断言线程，失败调用会留下部分状态修改。
- Channel/TimerQueue/EventLoop 的用户 callback exception 策略未统一，异常可能留下 processing 标记。
- TcpConnection::connectDestroyed 对 disconnecting 状态、回调内销毁 Server/Client、
  queued writeComplete 后的 owner 生命周期需要更多确定性合同。
- EventLoop quit 后没有显式拒绝/接收投递状态机；外部生产与销毁必须有调用方屏障。
- 基础背压暂停读取，不是 outputBuffer 内存硬上限；Acceptor 的 accept loop 也没有处理预算。
- Windows select、Socket option 返回值、TLS socket handle 转换和平台异常路径尚无完整行为矩阵。

这些是审计待办，不应扩展成一次不可审查的全库重写。

## 5. 研发方向为什么需要裁掉

### 5.1 默认构建才是真实架构边界

原 `CMakeLists.txt` 把 game、KCP、PMTU/raw ICMP、HTTP/WS/RPC、codec、exporter 全部
编入 mini_trantor，并安装全部 mini 头文件。运行时选项和实验测试标签没有隔离编译依赖、
发布 API 或维护责任。现在这些模块连同专属测试退出源码，Git 保存历史，当前库不再携带它们。

### 5.2 自研可靠 UDP 已从工具变成研究项目

原 KcpTransport.cc 为 1,899 行，组合可靠性、SACK、重传、MTU 探测、blackhole、
raw ICMP、cache、拥塞窗口、冗余副本和 XOR parity。KcpCodec 使用本项目自定义
22 字节帧头与 magic/version，本次没有外部 KCP 互操作证据，不能从类名推导兼容性。
这些职责与“先闭合 Reactor 生命周期”没有优先级上的合理关系，撤销继续生产化路线。

### 5.3 游戏接口已经进入核心

TcpServer 曾直接公开 bindBroadcastSession/joinBroadcastGroup/joinBroadcastAoi，
并拥有 Router/Dispatcher/PayloadPool。基础 MetricsHook.h 还声明 game/session/logic 类型。
GameServerPipeline 的 auth-ok、默认 room/aoi 和固定消息编号属于示例协议；
把它们以 core library 名义发布会形成长期业务兼容负担。

### 5.4 多条权威路线互相冲突

AGENTS 保留 v1 延期 timer 的说法，README 已有 Stable 与游戏网络定位，roadmap 推进到
v5/v6，另有两份评估/执行计划和 M1–M32 checklist。现在只保留一份当前路线，
所有旧路线、解释和已退出模块 intent 进入 docs/archive/pre-reset，并标为历史。

先执行[研发路线 S1](roadmap.md)的六类合同工作：frame 注销、suspend 发布顺序、DNS
重入/关闭、线程启动失败、回调生命周期、TLS 对端验证。每次只闭合一个可复现问题，
附 intent、回归、状态/时序图与五项 change gate。

在这些问题关闭、TSan 失败逐项解决、最小 TCP 行为矩阵和资源上限明确之前，不新增
协议、业务 pipeline、可靠传输控制或观测平台，也不重新声明 Stable。
